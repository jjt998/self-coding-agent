Phase 9 / Current Run Chain

self-coding-agent 任务运行链路图

这张图描述当前真实执行路径：入口完成配置、sandbox、setup 和 trace 初始化后，loop 只做 ingest -> analyze -> (plan -> act -> reflect)*，求解阶段退出后再执行一次末尾 verify -> finalize。它也标出模型决策契约、跨轮反馈、文件缓存污染治理和待修复风险。

状态机阶段 模型决策 工具执行 事实型 reflect 末尾验证与收口 审查发现 / 待办

总览：从入口到产物

当前主链路把“求解”和“裁判”分开。模型可以多轮读、改、查，但是否完成任务只在求解退出后由最终验证判定。

CLI / Eval

启动入口

python -m cli 接收单次任务或 eval/comparison 参数。

  • --task
  • --eval-task-file
  • --compare-strategies
Config

配置与密钥

加载 configs/*.json、.env 和系统环境变量。真实模型缺少 DEEPSEEK_API_KEY 会以 model_error 收口。

Workspace

准备 sandbox

per_task_sandbox 会把目标仓库复制到 .agent_sandboxes/<run_id>/repo，避免污染源仓库。

Trace

初始化产物

写入 config_snapshot.json、trace.jsonl、report.md、live_trace_view.html 和实时快照。

Setup

任务准备

执行 eval task 中的 setup_commands。失败会跳过求解 loop，直接生成 setup_failed 的结构化收口。

状态机主链路

ingest

输入摘要

记录任务文本、任务类型、repo/workspace 信息、setup/verify 数量、最大求解轮数和配置摘要。

analyze

上下文构建

根据任务关键词和 context 策略选择候选文件，生成 initial_guide，并读取 long-term memory。

solve loop

多轮求解

每轮固定执行 plan -> act -> reflect。runtime.max_steps 控制最大求解轮数，当前 configs/default.json 为 15。

verify

末尾单次验证

求解阶段退出后，调用 git_diff 快照，并执行任务级 verify_commands / verify_rules。

finalize

报告与清理

写入 finalize_summary 和 run_finished，再按 sandbox cleanup 策略保留或删除现场。

求解循环：verify 不在每轮内

旧图里的 (plan -> act -> reflect -> verify)* 已过时。现在 verify 是最终裁判，不再把验证失败反馈给下一轮模型。

plan

模型决策

构造 OpenAI compatible 请求，写入 model_request_prepared、model_raw_response、model_decision 和 token usage。

act

执行工具

只执行模型 JSON 中的 tool_calls。planned_actions 是展示字段，不会驱动工具。

reflect

事实压缩

每轮 act 后固定生成 reflect_content，压缩工具结果、失败工具、diff 信号和文件上下文缓存。

exit check

求解退出

tool_calls=[] 时记录 solve_loop_exit_reason=no_planned_tool_calls；达到最大轮数时记录 max_steps_reached。

继续下一轮的唯一事实输入

每轮 plan 前都会把 initial_guide 与最新 context_snapshot 一起交给模型；第二轮及以后，重点由 context_snapshot.working_memory、context_snapshot.fresh_context、context_snapshot.stale_context 和 context_snapshot.recent_facts 承载运行事实。

不再存在的反馈

链路中已移除 previous_verification 和 previous_reflect.verification。最终验证只用于收口、报告和 eval 聚合，不参与下一轮重规划。

模型决策契约

模型必须返回结构化 JSON。harness 会校验字段、工具名、工具入参和部分类型；决策文本和真实执行路径保持分离。

字段 当前语义 是否会驱动执行
summary 本轮决策摘要，进入 trace/report。 否
rationale 模型显式给出的判断理由；下一轮会由 harness 注入到 context_snapshot.working_memory.last_rational。 否
planned_actions 只能描述本轮 tool_calls 实际会做的事；不可当作跨轮任务队列。 否
working_memory 模型返回固定四字段：confirmed_facts、invalidated_beliefs、completed_actions、next_risks；输入快照中会额外带有 last_rational。 否
tool_calls 工具调用数组。工具名必须属于 schema，tool_input 必须是对象并通过字段校验。 是，唯一执行源

当前可用工具

search_text、 read_file、 read_file_structure_summary、 read_file_range、 apply_patch、 replace_lines、 run_command、 git_diff

收口信号

tool_calls=[] 不表示“已经通过验证”，只表示模型认为不需要继续求解。随后仍要经过最终 verify，最终 stop reason 由模型错误、setup 失败或验证结果决定。

initial_guide / context_snapshot 形状

initial_guide 是首轮任务、仓库召回和长期记忆指导；context_snapshot 是每轮 plan 前重建的运行时事实快照。

initial_guide

包含 task、repo_guide 和 memory_guide。其中 selected_files 只暴露结构摘要和推荐理由，不再注入不可控 summary。

context_snapshot.working_memory

上一轮模型返回的四字段工作记忆，加上 harness 从上一轮 rationale 注入的 last_rational。模型如果推翻了旧判断，需要自己写入 invalidated_beliefs。

fresh / stale / recent

fresh_context 放仍可信的片段、diff 和命令结果；stale_context 提醒哪些旧片段需重读；recent_facts 放最近工具结果、失败工具和 signals。

上下文窗口与文件缓存

初始上下文不会把整个仓库塞给模型。文件进入上下文前会先被筛选、打分和裁剪；大文件优先暴露结构摘要，再用精确行号补齐。

task

任务关键词

从任务文本抽取路径、标识符和关键字，用于候选文件召回。

scan

仓库文本扫描

扫描 repo root 内可按 UTF-8 读取的文本文件，并计算 candidate_file_count。

select

选择文件

按分数和路径排序，写入 initial_guide.repo_guide.selected_files；首轮只提供 structure_summary 和推荐理由，具体内容由模型后续主动读取。

large file

结构后精读

大文件优先使用 read_file_structure_summary 定位，再用 read_file_range 精确读取 1 到 80 行。

cache

stale / fresh

文件被 apply_patch 或 replace_lines 成功编辑后，旧片段标为 stale；重读后恢复为 fresh。

old_text_not_found 证据链

这块内容是回归测试固定的诊断口径：当模型猜错 apply_patch.old_text 时，下一轮必须看到失败文本摘要和可直接复制的候选源码片段。

反馈中应保留的字段

{
  "tool_name": "read_file",
  "path": "todo_app.py",
  "content_excerpt": "候选源码片段",
  "excerpt_reason": "old_text_not_found_candidate"
}
{
  "tool_name": "apply_patch",
  "path": "todo_app.py",
  "error": "old_text_not_found",
  "failed_old_text_excerpt": "失败的 old_text 摘要"
}

模型下一轮应如何利用

  • 从最近 read_file 或 read_file_range 的 content_excerpt 复制真实旧文本。
  • 把失败假设写入 working_memory.invalidated_beliefs。
  • 避免无解释地重复同一段错误 old_text。
  • 连续匹配困难时，优先考虑基于已确认行号的 replace_lines。

关键诊断词：content_excerpt、failed_old_text_excerpt、old_text_not_found_candidate、候选源码片段、失败的 old_text 摘要。

最终验证与收口

最终 verify

求解 loop 退出后，_run_verify 先生成 verification_diff_snapshot，再调用 build_phase_4_verification。验证结果写入 verification_result。

finalize

finalize_summary 记录最终状态、验证是否通过、变更文件、失败工具数、reflect 次数、实际求解轮数、模型决策数和 token usage。

主 stop reason

setup_failed 和 model_error 会提前收口；正常跑到最终验证后，验证通过为 completed，未通过为 verification_failed。

诊断细节

solve_loop_exit_reason 会进入 stop_reason.details。例如 no_planned_tool_calls 或 max_steps_reached 用于解释求解阶段为什么停止。

代码审查发现：待修复风险

下面是当前代码审查发现的风险，不代表系统已经完成防护。把它们放在链路图里，是为了排查 run 时能直接看到边界。

风险点 影响 建议方向
敏感文件扫描 context 和工具会读取 repo 内 UTF-8 文本；如果仓库里有 .env，存在被召回或读取进上下文的风险。 给 context scan、search_text、read_file 系列工具增加统一 denylist。
run_command 字符串命令使用 shell=True，且当前没有超时；模型若返回长跑命令，可能挂住任务。 默认拒绝字符串 shell 命令或强制数组命令，并为 subprocess 增加 timeout。
打包清单 pyproject.toml 的 py-modules 未包含 runtime_trace、file_structure、live_trace_view，安装后入口可能缺模块。 补齐模块清单，或改为更稳妥的 package discovery。
文档残留 README.md 仍有旧的 loop 和反馈字段描述，可能误导使用者。 后续把 README 与本页的 current run chain 对齐。
