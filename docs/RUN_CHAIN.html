Phase 9 / Run Chain

任务运行链路图

这张图把一次任务从 CLI / eval 入口、sandbox 准备、模型计划、工具执行、观察反思、验证收口到报告产物的路径串起来。 用它排查时，重点看 model_raw_response、tool_result、verification_result 和 reflect_feedback。

状态机阶段 模型决策 工具执行 验证与收口 失败证据 trace / 产物

入口与配置

CLI / Eval

启动入口

python -m cli 接收单次任务、eval batch 或 comparison 参数。

  • --task
  • --eval-task-file
  • --repo-root
Task Spec

任务定义

eval task 提供任务文本、任务类型、sandbox 策略、setup、verify 命令和 verify rules。

Config

模型与策略

configs/default.json 决定模型、最大轮数、context、reflect、memory 策略。

.env

API Key

从系统环境变量或 .env 读取 DEEPSEEK_API_KEY，不会写入 trace。

Workspace

准备 sandbox

per_task_sandbox 会复制目标仓库到 .agent_sandboxes/<run_id>/repo。

Trace

初始化产物

写入 config_snapshot.json、空 trace.jsonl 和初始 report.md。

执行主链路

prepare

workspace_prepared

记录源仓库、执行仓库、workspace mode 和 sandbox 目录。

setup

task_setup

执行任务准备命令。失败时直接 setup_failed 收口。

ingest

输入摘要

记录任务文本、任务类型、验证数量、最大轮数和配置摘要。

analyze

上下文构建

扫描文件、召回 memory，写入 context_snapshot。

loop

多轮求解

进入 harness 内部最多 runtime.max_steps 轮的 plan / act / reflect / verify 循环；轮数预算不进入模型请求。

finalize

收口报告

写入 run_finished、report.md，按策略清理或保留 sandbox。

上下文窗口如何填充

当前上下文不是把仓库全文塞给模型，而是在 analyze 阶段构造 context_snapshot， 再由 model._build_request_payload() 放进 user message。这个窗口由任务、仓库文件、运行态和 memory 四层组成。

1 task

提取任务关键词

从任务文本按空白、标点、路径分隔符切分，保留完整任务文本和关键词，例如 todo_app.py、list、[done]。

2 scan

扫描文本文件

只读取 repo root 内可按 UTF-8 打开的文件，跳过二进制或不可读文件。

3 score

文件打分

路径命中关键词加分，内容命中关键词加分；bug_fix 任务会额外提高 .py 和测试文件优先级。

4 select

选 Top 3

按 score desc, path asc 排序，只选最多 3 个文件进入 repo_context.selected_files。

5 inject

选择注入模式

根据分数和行数决定 original、summary 或 index，不是所有选中文件都给全文。

6 payload

进入模型请求

context_snapshot.to_dict() 被放入 OpenAI compatible 请求的 user message。

{ "task": "修复 demo todo app 的 list 状态显示 bug", "task_type": "bug_fix", "context_snapshot": { "task_context": { "task": "完整任务文本", "task_type": "bug_fix", "keywords": ["demo", "todo", "list", "bug"] }, "repo_context": { "candidate_file_count": 12, "selected_files": [ { "path": "todo_app.py", "injection_mode": "summary", "injection_content": "文件、总行数、前 8 条非空行", "score": 3, "was_clipped": true } ] }, "runtime_context": { "current_state": "analyze", "completed_states": ["ingest"], "step_count": 2 }, "memory_context": { "runtime_rules": [], "long_term_memory": [] } }, "runtime_feedback": { "previous_reflect": { "observation": "上一轮工具事实摘要", "signals": ["failed_tool_observed"], "recent_tool_results": [ { "tool_name": "read_file", "path": "todo_app.py", "line_count": 120, "content_excerpt": "候选源码片段", "excerpt_reason": "old_text_not_found_candidate" }, { "tool_name": "apply_patch", "path": "todo_app.py", "error": "old_text_not_found", "failed_old_text_excerpt": "失败的 old_text 摘要" } ], }, "previous_cross_round_plan": "上一轮模型给出的跨轮安排" }, "decision_schema": { "planned_actions": "只能描述本轮 tool_calls 实际会做的事", "cross_round_plan": "跨轮安排和后续轮次意图", "tool_calls": "唯一会被 act 阶段实际执行的工具调用" }, "tool_schema": { "apply_patch": { "required": ["path", "old_text", "new_text"], "properties": { "old_text": "string|null", "new_text": "string" } } } }
第一轮 plan：主要吃 context_snapshot 模型看到任务文本、召回文件摘要、runtime/memory 信息；如果关键源码行被 summary 裁掉，模型就没有可靠依据写精确 patch。
act 后：工具结果先进入 trace 和 runtime state read_file、apply_patch、run_command、git_diff 的结果都会记录，但不等于全文自动塞回下一轮 prompt。
第二轮 plan：叠加 runtime_feedback 下一轮会收到观察摘要、最近工具结果摘要、验证结果、reflect_feedback 和 previous_cross_round_plan；旧风险是工具摘要过短，只告诉模型读了多少行，却没给关键源码片段。 改进后，read_file 摘要会携带 path、短 content_excerpt 和行号范围。
精确 patch 的安全路径 如果模型要调用 apply_patch，理想输入应包含来自 read_file 的真实源码行；否则 old_text 容易变成猜测。 当出现 old_text_not_found 时，反馈会携带失败 old_text 摘要和候选源码片段。

四层 context_snapshot

  • task_context：任务文本、任务类型、关键词。
  • repo_context：候选文件数、选中文件、注入内容、裁剪信息。
  • runtime_context：当前状态、已完成状态、step count。
  • memory_context：runtime rules、long-term memory、冲突诊断。

打分倾向

  • 路径包含任务关键词：更容易被选中。
  • 内容包含任务关键词：分数更高。
  • bug_fix：偏向代码文件和测试文件。
  • naive_recent_context：改为按最近修改时间选文件。
注入模式 触发条件 进入模型的内容 风险
original 分数至少 4，且文件不超过 40 行。 最多前 40 行原文。 短文件最可靠，模型能直接复制真实 old_text。
summary 分数至少 3，但文件较长。 文件名、总行数、前 8 条非空行摘要。 可能裁掉关键实现行；最近 todo_app.py 就因此没把状态逻辑放进初始 prompt。
index 低分文件或只需要轻量提示。 文件名、总行数、前 5 条非空行拼成索引提示。 只能提示文件存在，不能支撑精确 patch。

最近失败暴露的上下文缺口

初始 context_snapshot 里 todo_app.py 是 summary 模式，只包含文件前几行， 没包含真实代码 status = "todo" if task.get("done") else "done"。 旧版后续虽然 read_file 读到了全文，但 runtime_feedback.recent_tool_results 只保留 line_count， 没把关键源码行交回下一轮 plan，于是模型继续猜错 apply_patch.old_text。

改进后，recent_tool_results 会为 read_file 保留短源码片段； 遇到 old_text_not_found 时，还会把失败 old_text 和候选源码行一起交给下一轮。

模型决策契约与工具 schema

模型不是直接“自由发挥”调用 Python 函数，而是先返回一份结构化 JSON 决策。 plan 阶段解析这份 JSON，act 阶段只执行 tool_calls。 这层契约的目标是让跨轮计划、当前轮说明和真实工具执行分开，避免“文字说要修，但实际只读文件”的歧义继续扩大。

字段 定位 是否执行 风险与缓解
summary 本轮模型决策摘要。 否 只用于 trace/report 阅读。
rationale 解释为什么本轮这样安排，也用于观察是否回应 reflect 证据。 否 不会获取 provider 隐藏推理链，只记录模型显式返回内容。
planned_actions 本轮 tool_calls 实际会做什么的可读说明。 否 不是跨轮任务队列；如果模型把未来计划写在这里，页面和报告会误导人，但 loop 仍只执行 tool_calls。
cross_round_plan 跨轮安排、后续轮次意图、暂不执行的计划。 否 下一轮会通过 runtime_feedback.previous_cross_round_plan 回填给模型。
tool_calls 工具调用数组，包含 tool_name 和 tool_input。 是 唯一执行源；工具名、字段名、必填项和字段类型都会被校验。

字段名校验

模型只能传入 tool_schema 声明过的字段。比如 read_file 只接受 path，常见别名 file_path 会先归一化。

类型校验

string、integer、null、array 和数组元素类型都会被检查。

已缓解的崩溃点

如果模型返回 apply_patch.new_text = null，现在会收口为 ModelResponseError / model_error，不再进入 Path.write_text(None) traceback。

多轮 Loop 细节

plan

模型计划

请求 OpenAI compatible 模型。写入 model_raw_response、model_decision 和本次请求的 token_usage。

act

工具执行

按 tool_calls 依次执行 read_file、apply_patch、run_command、git_diff。

reflect

事实压缩

每轮 act 后固定执行，写入 reflect_feedback，只保真压缩事实和轻量 signals。

verify

任务验证

执行 verify_commands 和 verify_rules，写入 verification_result。

next plan

事实回灌

验证失败且仍有预算时，上一轮事实通过 runtime_feedback.previous_reflect 进入下一轮 plan。

循环规则

验证通过：直接进入 finalize。

验证失败且仍有预算：携带 runtime_feedback 回到下一轮 plan。

达到最大轮数：以 verification_failed 或 max_steps_reached 收口。

模型与工具证据链

模型原始返回

model_raw_response 保存模型显式返回的 JSON content 和本次请求的 token_usage。排查模型“嘴上说要改但 tool_calls 没改”或单任务 token 异常时先看这里。

结构化模型决策

model_decision 保存解析后的 summary、rationale、planned_actions、cross_round_plan、tool_calls。

planned_actions 只解释本轮真实执行动作，cross_round_plan 才是跨轮安排；tool_calls 是唯一执行源。

工具调用结果

tool_called 和 tool_result 显示实际执行了什么，以及是否 ok。

反思事实

reflect_feedback 记录工具结果、失败工具、变更文件和 signals；harness 不判断上一轮是否“有效”。

验证失败

verification_result 展示失败检查项，例如 command stdout 不匹配、diff 未包含目标文件。

反思输入

reflect_feedback 进入下一轮 runtime_feedback.previous_reflect；模型看不到当前轮数、剩余轮数或最大轮数。

最近真实问题链路：old_text_not_found

read_file

源码证据

工具读到了真实代码：status = "todo" if task.get("done") else "done"。

model

模型猜错 old_text

模型返回了不存在的 old_text：status = "[done]" if task["done"] else "[todo]"。

apply_patch

工具失败

apply_patch 返回 old_text_not_found，所以文件没有变化。

verify

验证失败

git_diff 没有变更，python todo_app.py list 仍输出错误状态。

这个问题暴露出的改进点：prompt 应要求 apply_patch.old_text 必须逐字来自最近 read_file 内容； reflect_feedback 应携带失败 old_text 和候选源码行，而不是只传摘要。

大文件上下文与低摩擦编辑链路

read_file

小文件完整，大文件摘要

小文件返回 content_mode="full" 和完整内容；超过阈值的大文件返回 content_mode="structure_summary"、content_truncated=true 与 structure_summary。

read_file_structure_summary

先拿结构，再精读

如果只需要先定位函数、类、标题和起始行号，模型应优先调用 read_file_structure_summary(path)；若缺关键源码，再调用 read_file_range(path,start_line,end_line) 精确读取闭区间行号范围。

replace_lines

按行替换降低摩擦

当同一文件连续出现 old_text_not_found，尤其接近 3 次时，优先基于最近源码行号使用 replace_lines，避免继续猜测大段 apply_patch.old_text。

git_diff / verify

用事实闭环

编辑后继续用 git_diff 与任务级 verify_commands / verify_rules 判断是否真的产生目标变化。

风险点：大文件不会被全文塞入下一轮模型上下文。缓解方式是让 structure_summary 暴露可定位行号， 再由 read_file_range 精确补齐，最后用 replace_lines 做小范围编辑。 文件一旦编辑，旧读取缓存会整文件标记为 stale，避免模型继续引用编辑前片段。

产物与诊断

单次 run 产物

  • trace.jsonl：完整事件流。
  • report.md：人类可读报告，包含单任务 token 消耗。
  • config_snapshot.json：本次运行配置快照。

eval / comparison 产物

  • summary.json：聚合指标、failure taxonomy 和 token usage 汇总。
  • summary.md：人类可读评测汇总。
  • task_deltas：策略对比时查看任务级变化。

stop reason

常见值包括 completed、setup_failed、model_error、verification_failed、max_steps_reached。

sandbox cleanup

sandbox_cleanup_result 记录是否保留 sandbox。keep_on_success 表示只保留成功任务现场。

如何看最近一次 run

先打开最新 eval 的 summary.json，确认 stop_reason、失败检查、taxonomy 和 token 汇总。
再看单次 run 的 report.md，快速读取状态流、模型返回摘要、Token 消耗、进展观察和验证结果。
回到 trace.jsonl，按顺序查 model_raw_response、model_decision、tool_result；需要拆轮分析 token 时看每条 token_usage。
如果是 model_error，先看 model_decision_failed 的 field_path、tool_name、expected_type、actual_type，判断是否是工具入参 schema 错误。
如果工具失败，定位 error，例如 old_text_not_found、命令返回码非 0、未知工具参数。
如果验证失败，查看 verification_result.checks，确认是命令输出、diff、文件内容还是规则不满足。
最后看 reflect_feedback 是否把失败证据足够具体地交给下一轮 plan。
